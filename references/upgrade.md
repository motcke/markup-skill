# Mode: upgrade

Read from `SKILL.md` when `/markup upgrade` runs or a `wait` line says `UPGRADE`. `SKILL`, `USER`, `PROJECT` and `SESSION` mean what they mean there.

A clean install never gets here: the balloon's "Upgrade" button upgrades it without an agent. This mode is for an install where the user changed shipped files; the user asked that someone look at what they added before an upgrade, and that the upgrade keep it.

1. `node "SKILL/server.mjs" version "PROJECT"` prints `version`, `kind` and the changed files. `dev` (a git checkout): tell the user to run `git pull` in `dir`, stop. `clean`: run `node "SKILL/server.mjs" upgrade "PROJECT"`, report the new version, stop.
2. `node "SKILL/server.mjs" upgrade "PROJECT" prepare` builds a workspace (`USER/upgrades/<from>-to-<to>/`) and writes nothing into `SKILL`. Its JSON lists `keep` (the user changed it, the release did not), `merge` (both changed it; `merged` is `clean`, `conflicts`, or `null` when git is missing), `ask` (the release removed a file the user changed) and `userChanged`. In the workspace: `ours/` (the user's files), `base/` (as the user received them), `theirs/` (the release), `merged/` (a three-way merge), `plan.json` (one entry per file).
3. Spawn one subagent (a cheaper model is fine) with the workspace path and this brief: for every file in `userChanged`, compare `ours/<f>` with `base/<f>` and say in one line what the user changed; for every `merge` file, finish `merged/<f>` so the user's change and the release's change both survive, with no conflict markers left (when they truly contradict, say which side wins and why); for every change, say whether it fits an extension point in `SKILL/docs/extensions.md` (a style → `USER/ext/*.css`, a component → `USER/ext/*.js`, a library → `USER/ext/vendor/`, a rule → `USER/rules.md`, a check → `USER/ext/checks/`) and give the exact file to write. Return a table: file · user change · release change · result · extension proposal.
4. Publish a markup page (slug `markup-upgrade`): the release notes, the subagent's table with traffic lights (kept / merged / conflict resolved), the user's changes as `.diff` blocks, and `.q` questions: apply the upgrade (yes / not now), one per `ask` file (keep / delete), one per extension proposal (move / leave in the skill folder). Arm `wait`.
5. After the picks: set `"decision": "keep"` or `"delete"` on each `ask` entry in `plan.json`. For each approved extension move, write the extension file under `USER/ext/` (or the rule into `USER/rules.md`) and set that entry's `"action": "take"` in `plan.json`, so the skill file goes back to the release version and the change lives in the extension from now on.
6. `node "SKILL/server.mjs" upgrade "PROJECT" apply "<workspace>"`. It refuses while a merge has conflict markers or an `ask` has no decision; it backs up every file it touches to `USER/backups/` and restarts this project's server on the new code. Report the new version, the kept files and the rollback command (`upgrade "PROJECT" rollback`). If an `UPGRADE` line started this, run `done` on the plan it named.

Never edit files under `SKILL` by hand during an upgrade: everything goes through the workspace and `apply`, so the backup and the manifest stay true.
